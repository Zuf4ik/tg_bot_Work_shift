# Work Shift Tracker Bot

**Work Shift Tracker** — Telegram-бот для учёта рабочих смен, расчёта заработка и планирования рабочего времени. Проект написан на **Go**, использует **PostgreSQL** для хранения данных и предоставляет отдельный **REST API**.

Бот создан для практической задачи: вместо ручного подсчёта часов и доплат можно сохранять смены, видеть текущий заработок и сравнивать его с планом на месяц.

> **Статус:** рабочая версия, развивается. Формулы выплат отражают правила, заложенные в коде; итоговые начисления работодателя могут отличаться.

## Возможности

- **Интерактивный календарь:** переход между месяцами, отображение дней со сменами и подробностей выбранной смены.
- **Управление сменами:** добавление, редактирование времени, перерыва и ставки, удаление с подтверждением.
- **Учёт рабочего времени:** расчёт оплачиваемых часов с учётом перерыва и контроль пересечений смен.
- **Дополнительные работы:** разгрузка, вынос мусора и доставка.
- **Месячная сводка:** завершённые и запланированные часы, норма месяца, оставшиеся часы, процент выполнения и рассчитанная премия.
- **Статистика дохода:** текущий месяц, предыдущий месяц или произвольный период; фактические и ожидаемые выплаты учитываются отдельно.
- **Настраиваемая почасовая ставка:** сохраняется для пользователя в PostgreSQL.
- **Проверки данных:** контроль формата даты и времени, диапазона ставки, длительности перерыва и принадлежности смен пользователю.

### Главное меню

| Раздел | Назначение |
| --- | --- |
| `➕ Добавить смену` | Выбрать дату в календаре и ввести параметры смены |
| `🗓 Календарь смен` | Посмотреть смены и перейти к действиям с ними |
| `📊 Статистика` | Получить отчёт за месяц или выбранный период |
| `📦 Дополнительные работы` | Привязать доплаты к конкретной смене |
| `💰 Указать ставку` | Задать часовую ставку для новых смен |

Редактирование и удаление смен доступны из календаря. Отдельный экран истории смен убран, чтобы не дублировать календарь и статистику.

## Пример месячной сводки

```text
🗓 Календарь смен — 11.2026

✅ Отработано: 24.75 ч.
📅 Запланировано: 11.00 ч.
🎯 Норма месяца: 159.00 ч.
⌛ Осталось до нормы: 134.25 ч.
📊 Выполнено: 15.6%
🏆 Премия: 0.00 ₽

💰 Заработано: 8895.00 ₽
```

*Пример из тестирования интерфейса; значения не являются демонстрацией полного рабочего месяца.* Смена учитывается в месяце **по дате начала**. Завершённые смены включаются в фактический доход, незавершённые — в прогноз. Это техническая классификация по времени окончания, а не подтверждение фактического выхода сотрудника на работу.

## Как рассчитывается заработок

### Продолжительность смены

```text
Оплачиваемые часы = (время окончания − время начала) − перерыв
```

Если время окончания относится к следующему дню, бот учитывает переход через полночь. Для отображения времени используется часовой пояс `Asia/Yekaterinburg` (UTC+5); даты смен хранятся в PostgreSQL как `TIMESTAMPTZ`.

### Временные надбавки

| Период | Коэффициент |
| --- | ---: |
| 07:00–22:00 | ×1.0 |
| 22:00–00:00 | ×1.2 |
| 00:00–07:00 | ×1.3 |

В текущей реализации оплата рассчитывается по минутам, а стоимость перерыва вычитается по **базовой ставке**: точный момент перерыва бот не хранит. Для смены **22:00–07:00** с перерывом **45 минут** и ставкой **300 ₽/ч** текущий алгоритм возвращает **3 225 ₽**. Это поведение кода, а не гарантия соответствия расчётному листку работодателя.

### Дополнительные работы

| Работа | Доплата |
| --- | --- |
| Разгрузка | 2 × часовая ставка |
| Вынос мусора | 0,25 × часовая ставка |
| Доставка | (оплачиваемые часы / 2) × часовая ставка |

Доплаты увеличивают сумму, но не прибавляют часы к продолжительности смены.

### Месячные премии

В коде используется **не суммируемая** шкала: применяется один максимальный достигнутый порог.

| Условие | Премия |
| --- | ---: |
| От 80 часов | 1 500 ₽ |
| От 120 часов | 3 000 ₽ |
| От 140 часов | 8 000 ₽ |
| Достижение месячной нормы | 15 000 ₽ |

Месячная норма загружается из таблицы `production_calendar` и может различаться по месяцам. Премия рассчитывается отдельно от основной зарплаты. Значения и правила специализированы под используемую в проекте систему оплаты.

## Запуск локально

### Требования

- Go **1.26** (версия указана в `go.mod`).
- Работающий PostgreSQL и созданная база данных.
- Telegram-токен бота, полученный через BotFather.
- Корректная локальная конфигурация приложения.

**1. Клонируй репозиторий:**

```bash
git clone https://github.com/Zuf4ik/tg_bot_Work_shift.git
cd tg_bot_Work_shift
```

**2. Настрой PostgreSQL и окружение.** Приложению нужны настройки подключения к БД и токен Telegram-бота. Для API дополнительно требуется `API_KEY`, для подключения Telegram через прокси — `USE_PROXY=true` и `SOCKS5_PROXY=socks5://...`.

> **Важно для установки:** рабочий `config/config.go` и секреты конфигурации не входили в архив, предоставленный для рефакторинга. Проверь названия переменных и фактический путь загрузки `.env` в **своей локальной версии** `config/config.go` перед публикацией инструкций для сторонних пользователей. В рабочей конфигурации проекта использовался файл `config/.env`. Не коммить `.env`, токены и пароли.

В PostgreSQL приложение ожидает таблицы `users`, `shifts`, `shift_extras` и `production_calendar`. Автоматические миграции и SQL-файлы создания схемы **не входят в проверенную версию репозитория**; базу нужно подготовить отдельно. Для хранения времени смен должны использоваться колонки типа `TIMESTAMPTZ`.

**3. Установи зависимости и запусти бота:**

```bash
go mod download
go run ./cmd/bot
```

По умолчанию бот подключается к Telegram напрямую. Для работы в сети, где доступ к Telegram ограничен, можно включить SOCKS5 в конфигурации.

> Не запускай одновременно локальную и серверную версии с одним токеном при использовании long polling: они могут конфликтовать при получении обновлений Telegram.

## REST API

Запускается отдельно от Telegram-бота:

```bash
go run ./cmd/api
```

По умолчанию слушает **`127.0.0.1:8080`**.

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| GET | `/health` | Проверка доступности процесса |
| GET | `/api/shifts?telegram_id=...` | Список смен пользователя |
| POST | `/api/shifts` | Создание смены |
| GET | `/api/shifts/{id}?telegram_id=...` | Получение смены по ID |
| PUT | `/api/shifts/{id}?telegram_id=...` | Обновление смены |

Все маршруты `/api/shifts...` требуют заголовок:

```http
Authorization: Bearer <API_KEY>
```

Формат времени в JSON — `YYYY-MM-DDTHH:MM:SS`, который интерпретируется в `Asia/Yekaterinburg`.

Пример JSON-тела для `POST /api/shifts`:

```json
{
  "telegram_id": 123456789,
  "start_time": "2026-11-20T16:00:00",
  "end_time": "2026-11-21T00:00:00",
  "break_minutes": 45,
  "hourly_rate": 300
}
```

ID здесь демонстрационный. Для `PUT` идентификатор пользователя передаётся в query-параметре `telegram_id`, а идентификатор смены — в URL.

**Ограничение безопасности:** API использует один общий ключ и не устанавливает права отдельного Telegram-пользователя. Не публикуй API в открытом интернете как многопользовательский сервис без отдельной аутентификации и авторизации. `/health` не требует API-ключа.

## Развёртывание на VPS

В рабочем окружении бот запускается на Ubuntu как сервис `systemd`, база PostgreSQL работает отдельно, а при необходимости используется локальный SOCKS5-прокси.

Общий порядок обновления после проверки кода:

```bash
# В каталоге проекта на сервере
git pull --ff-only origin master
go test -count=1 ./...
go build -o bot.new ./cmd/bot

# Остановить работающий процесс и заменить бинарник
sudo systemctl stop tg-bot.service
cp bot bot.backup
mv bot.new bot
sudo systemctl start tg-bot.service
sudo systemctl status tg-bot.service
```

Перед заменой бинарника убедись, что путь `ExecStart` в `tg-bot.service` указывает на файл `bot` именно в этом каталоге. Сохраняй конфигурацию и данные PostgreSQL отдельно от Git. При неполадках смотри логи через `journalctl -u tg-bot.service`.

## Ограничения и развитие

- **Статус смен:** сейчас завершённость определяется временем окончания, а не подтверждением фактического выхода на работу.
- **Надбавки:** точное время перерыва не хранится, поэтому распределение перерыва между тарифными зонами приблизительное.
- **Проверка пересечений:** реализована на уровне сервиса; для конкурентных запросов может понадобиться ограничение на уровне PostgreSQL.
- **База данных:** стоит добавить версионируемые SQL-миграции и инструкцию первого развёртывания с нуля.
- **REST API:** для внешних клиентов нужна индивидуальная авторизация и дополнительные меры защиты.
- **Тестирование:** дальнейшее направление — автоматические Telegram E2E-тесты с отдельным тестовым аккаунтом.
